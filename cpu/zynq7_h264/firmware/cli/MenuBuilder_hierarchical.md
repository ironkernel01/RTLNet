# MenuBuilder — hierarchical extension (network-switch style CLI)

| Item | Value |
|---|---|
| Revision | 10-22-2026 |
| Extends | MenuBuilder (`FUNCTION:COMMAND:DESCRIPTION` menus, explicit `matched` dispatch, aligned help) |
| First user | RTLNet Nexys Video firmware console (`cpu/microblaze_v_h264/firmware/cli`) |
| Input | `cli/cli_commands.txt` |
| Generator / checker | `cli/gen_menu.py`, `cli/check_menu.py` |

This document specifies a light-weight hierarchical command line in the style of a network switch
(user exec, privileged exec, configuration mode and sub-modes, `exit`/`end`, context-sensitive `?`,
abbreviations) built on the MenuBuilder rules. Everything MenuBuilder requires still holds unless a
section below says it is replaced.

## 1. What is kept from MenuBuilder

- Commands are defined in a `.txt` file, one per line, `#` comments, colon-separated fields, keywords
  case-insensitive, `[NAME]` required and `{NAME}` optional parameters, optional parameters last.
- The parser pre-parses every syntax at `Menu_Init()` and dispatches through
  `menu_match_and_dispatch(..., &matched)`: `matched = 1` only after the token count, every keyword and
  every required parameter check out and the definition has an action; dispatch stops only on
  `matched == 1` (MenuBuilder section 6).
- Help output is aligned on one `" - "` column computed from the longest entry; `HELP` and `?` print
  the same listing (MenuBuilder section 9).
- Every generated or engine `.c`/`.h` starts with the LGPL 2.1 block, then a file header block, and
  every `.c` carries the `MM-DD-YYYY` revision table; every function has a Doxygen block.
- `build.bat` and `Makefile` build the desktop harness (`menu.exe`) with
  `-std=c11 -Wall -Wextra -Werror -pedantic -O2`; `demo` runs the scripted session;
  `MenuDocumentation.md` with the Mermaid diagrams is generated from the `.txt`.

## 2. What is replaced

| MenuBuilder rule | Hierarchical rule |
|---|---|
| Keywords must match exactly | A keyword may be abbreviated to any prefix that is unique among the keywords valid at that position (`sh ver`); an exact match always wins (`ip` beats `iperf`) |
| One flat command list | Commands belong to a mode; only the commands of the current mode (and, in privileged exec, those of user exec) are matched |
| `?` is an alias of HELP only | `?` on an empty line is HELP; after text it is context help (section 6) |
| Generated `main.c` / `menu_callback_Test.c` | The callbacks are the real `cli_commands.c`; the harness is `host/main.c` + `host/host_platform.c` (register model), so the desktop demo runs the target's command code |
| Output through `printf` | The engine has no C-library dependency; it writes through a `MenuIo.write` hook (the target links no C library) |

## 3. Input format

Five line kinds. Fields are separated by `:`; the last field may contain colons.

| Line | Fields |
|---|---|
| `REVISION:<MM-DD-YYYY>:<change>` | revision history of the command set; the newest date is the generation date |
| `MODE-ROOT:<mode>:<prompt>:<mode description>` | the root mode (exactly one, `exec`) |
| `MODE-ENTER:<FUNCTION or ->:<from mode>:<COMMAND>:<to mode>:<prompt>:<mode description>:<DESCRIPTION>` | a command of `<from mode>` that enters `<to mode>`; defines that mode's prompt, its description and its parent (`<from mode>`, where `exit` returns) |
| `KEYWORD:<mode>:<KEYWORD PATH>:<DESCRIPTION>` | help text of a keyword shared by several commands (`SHOW`, `NO IP`) |
| `<FUNCTION>:<mode>:<COMMAND>:<DESCRIPTION>` | an ordinary command |

Modes are a fixed set (they are an enumeration in `menu.h`):

| Mode | Prompt (RTLNet) | Role |
|---|---|---|
| `exec` | `rtlnet>` | user exec: show commands |
| `priv` | `rtlnet#` | privileged exec: debug, LEDs, reload, show running-config; all exec commands too |
| `config` | `rtlnet(config)#` | global configuration |
| `config-if` | `rtlnet(config-if)#` | interface configuration |
| `config-dhcp` | `rtlnet(config-dhcp)#` | DHCP client configuration |
| `config-sock` | `rtlnet(config-sock)#` | UDP socket configuration |

Rules checked by the generator (`gen_menu.py` refuses the file otherwise):

1. Every mode of the set is defined exactly once (MODE-ROOT for `exec`, one MODE-ENTER for each other).
2. FUNCTION names are lower_snake_case C identifiers, unique; `-` only on MODE-ENTER (mode change
   without a callback). A MODE-ENTER callback returning nonzero rejects the entry (`interface eth1`).
3. Keywords are upper case letters, digits and `-`; parameters `[A-Z0-9_]`; at most 14 tokens of at
   most 23 characters and at most 14 parameters (`MENU_MAX_SYNTAX_TOKENS`, `MENU_MAX_TOKEN_TEXT`,
   `MENU_MAX_ARGS`).
4. No two commands available in one mode have the same shape (same keywords, parameters in the same
   places); exec commands count in priv.
5. No command may start with a built-in keyword (`EXIT`, `END`, `HELP`).
6. Negation is spelled out: `NO <command>` is an ordinary command whose first keyword is `NO`
   (`NO SHUTDOWN`, `NO IP ADDRESS`); `KEYWORD:<mode>:NO:...` gives `no ?` its help text.

## 4. Built-ins

| Built-in | Modes | Effect |
|---|---|---|
| `exit` | all | to the parent mode; at the root: "% Already at the top level" |
| `end` | priv and the configuration tree | to privileged exec (no effect in priv) |
| `help` | all | aligned listing of the mode's commands (identical to `?` on an empty line) |
| `?` | all | help, or context help after text (section 6) |
| `!!` | all | repeat the previous command line |
| Ctrl-Z | all | `end` (configuration tree), cancels the line |
| Ctrl-C | all | cancel the line (`^C`) |
| Ctrl-U | all | erase the line |
| Backspace / DEL | all | erase one character |
| ESC [ A / ESC [ B | all | previous / next history line (8 entries) |

## 5. Matching

For a typed line of n tokens, the resolver walks positions 0..n-1 over the candidate commands of the
current mode (commands whose syntax is shorter than the position drop out):

1. a keyword equal (case-insensitive) to the token keeps only the commands with that keyword there;
2. else exactly one distinct keyword that the token abbreviates does the same;
3. else two or more such keywords: `% Ambiguous command: "<token>"`;
4. else the commands with a parameter at that position stay, the token is the parameter value;
5. else `% Invalid input detected at '^' marker.` with a caret under the token.

The expanded tokens (keywords written out) then go through `menu_match_and_dispatch()` for each
surviving candidate in table order. No match: `% Incomplete command.` when a candidate needs more
tokens, else `% Unknown command or too many parameters.`

## 6. Context help

`?` is acted on when typed (it is not stored in the line); the line is redisplayed afterwards.

- empty line: the full aligned listing of the mode (same as `help`);
- text ending in a space (`show ?`): every keyword and `<parameter>` that may follow, and `<cr>` when
  the text is already a complete command; a keyword shared by several commands shows its KEYWORD
  text, otherwise the command's description;
- text ending in a partial word (`sh?`): the keywords it can complete to.

## 7. Files

| File | Kind | Content |
|---|---|---|
| `cli/cli_commands.txt` | source | the command set |
| `cli/gen_menu.py` | tool | writes the three generated files; `--check` compares only |
| `cli/check_menu.py` | tool | regenerates in memory and requires byte equality; checks that every FUNCTION is defined once in `cli_commands.c` with the callback signature and that no extra callback exists; checks Doxygen blocks; prints `CHECK PASS:` / `CHECK FAIL:` |
| `cli/menu_table.c`, `cli/menu_commands.h` | generated | mode, command and keyword tables; callback prototypes |
| `cli/MenuDocumentation.md` | generated | design document, Mermaid diagrams, command reference |
| `cli/menu.h`, `cli/menu.c` | engine | modes, resolver, dispatcher, help, line editor, history |
| `cli/cli_commands.c`, `cli/cli_commands.h` | callbacks | command implementations, banner, running configuration |
| `host/main.c`, `host/host_platform.c` | harness | stdin/stdout console, register model, `--demo` |
| `build.bat`, `Makefile`, `build.ps1` | build | harness and firmware |

Generation is reproducible: every output is a pure function of the `.txt` (the generation date is the
newest REVISION date), so a hand edit of a generated file or a stale table fails `check_menu.py`, which
`build.ps1` runs before every build.

## 8. Harness demo

`menu.exe --demo` types a scripted session character by character into `Menu_InputChar()` and checks
the console text and the mode after every step: abbreviations, ambiguity and invalid-input errors,
`?` and context help (alignment included), every mode and prompt, `exit`/`end`/Ctrl-Z, rejected
mode entries, history (`!!`, up arrow), backspace, Ctrl-C, the core-absent messages, a core made
present in the register model, the running configuration and reload. It prints exactly one line
`TEST PASS: menu_demo checks=<n>` or `TEST FAIL: menu_demo ...`; `--demo --inject-failure` must
print `TEST FAIL` (negative control, run by `build.ps1 -Demo`).

## 9. Example

```
MODE-ROOT:exec:rtlnet>:User exec
MODE-ENTER:-:exec:ENABLE:priv:rtlnet#:Privileged exec:Enter privileged exec mode
MODE-ENTER:-:priv:CONFIGURE TERMINAL:config:rtlnet(config)#:Global configuration:Enter global configuration mode
MODE-ENTER:cli_enter_interface:config:INTERFACE [IFNAME]:config-if:rtlnet(config-if)#:Interface configuration:Configure an interface (eth0)
KEYWORD:exec:SHOW:Show running system information
cli_show_version:exec:SHOW VERSION:Board, register map, build and firmware identity
cli_if_shutdown:config-if:SHUTDOWN:Disable the interface
cli_if_no_shutdown:config-if:NO SHUTDOWN:Enable the interface
```

```
rtlnet>sh ver
...
rtlnet>enable
rtlnet#conf t
rtlnet(config)#int eth0
rtlnet(config-if)#no ?
  shutdown   - Enable the interface
  ip         - Remove the static IPv4 address
rtlnet(config-if)#no shutdown
rtlnet(config-if)#^Z
rtlnet#
```
